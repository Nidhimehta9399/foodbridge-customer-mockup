Foodbridge Module Customer — Discovery Prototype

Can a wholesaler admin find, add, edit, tag, delete and act on the customers registered under their organisation — both B2B (wholesale, tax-registered, catalogue-mapped) and Retail (private, campaign-linked) — from a single Customer Management surface?

Frozen snapshot · v1

Customer Management — B2B & Retail Customers

HTML replica of the live storefront-admin Customer Management group, built from the app source and the As-is capture. Search, tag filter chips, row selection with bulk Delete / Assign tags / Send Campaign Link, the Add/Edit drawer (GST type, opening balance, billing vs shipping address), delete confirmation, Stock and Offers drawers, the “Send Ordering Link” and “Create Campaign Links” modals, CSV import preview and export (tenant-gated — off by default in this seed), pagination, and the mobile sticky bar. Every action mutates seed data and persists for the session.

Open B2B Customers → Open Retail Customers → Module hub

Screens

Screen 01 · /customers

B2B Customers

Entry point. List, search, tag chips, Import/Export, bulk actions, Stock and Offers per row, Add/Edit drawer, delete confirm.

 Screen 02 · /retail-customers

Retail Customers

Same table, private-customer variant: Send Ordering Link replaces Stock, no GST/import/tags, bulk Create Campaign Links.

Add, Edit, Stock, Offers and the tag editor are drawers; delete confirmation, campaign links and import preview are modals — all over the current list. Neither screen navigates away, which is why there are only two pages.

Data for both screens comes from seed-data/seed.json, mirrored verbatim in screens/customers/seed.inline.js because the prototype runs from file:// and cannot fetch local JSON — edit both together. It is seeded into localStorage so add/edit/delete/import persist while clicking between screens in one browser session; reset with FB.reset() in the console, or by clearing site data. Tenant feature flags live in the same seed under appProp — the As-is capture is one tenant's configuration, not the whole surface.

Screen scripts load in order: icons.js (real lucide / react-icons glyphs) → seed.inline.js → shell.js (sidebar, topbar, drawer / modal / menu / toast primitives) → customers.js (both screens). The _smoke/ jsdom boot check is a dev tool, not part of the prototype — it is not included in this frozen snapshot (see the live discovery/ tree for it).
